Spec 1 — The Sovereign Schema Matrix

A concrete zero-trust data contract schema (Protocol Buffers + JSON Schema) for cross-border public-private procurement sharing.

5 schemas in v1.0.0:

  • Tender — the canonical procurement opportunity record (matches the existing services/tenders-ingestor/internal/domain/tender.go struct)
  • ComplianceAssessment — Compliance Reasoner's output (with match_confidence, NOT win_probability)
  • BidDraft — Bid Drafter's output (with Word document S3 URL + provenance footnotes)
  • PartnershipCitation — for Indigenous-nation revenue-share accounting (5% revenue share, smart-contract payout tracking)
  • ResidencyGuarantee — the Bi-National Query Mesh's response wrapper (hash-anchored residency guarantee field)

Why both Protocol Buffers + JSON Schema: Protocol Buffers for binary serialization (low-bandwidth, schema-evolution-friendly, strong typing across languages); JSON Schema for human-readable validation and API documentation.

Schema evolution: additive only (new fields get new numbers; old fields never removed). Major version bumps require Federation Council ratification. Backward compatibility for ≥2 minor versions.

Full schema definitions in docs/architecture/16-tech-stack-evaluation-and-specs.md §3.1 (private repo)

Spec 2 — The Agent Workflow Definition

Complete LangGraph state machines detailing human-in-the-loop validation for multi-jurisdiction municipal bidding.

The 7-state bid-drafting workflow:

[START]
  ↓
[tender_ingested]              ← event: tender.published
  ↓
[capability_matched]           ← match_confidence > 0.7?
  ↓ (yes)
[compliance_assessed]          ← HUMAN CHECKPOINT #1 (user reviews)
  ↓ (user approves)
[bid_drafted]                  ← HUMAN CHECKPOINT #2 (user reviews + edits)
  ↓ (user approves)
[bid_ready_for_submission]     ← HUMAN CHECKPOINT #3 (user clicks "Submit")
  ↓
[bid_submitted]                ← IRREVERSIBLE — triggers PartnershipCitation
  ↓
[END]

Multi-jurisdictional sub-graphs: separate validation rules per jurisdiction (US federal / BC / WA / OR) — each is a LangGraph conditional edge with jurisdiction-specific validators.

Irreversible states (cannot be entered without explicit user click): bid_submitted. Triggers external API call to procurement portal + PartnershipCitation event for Indigenous-nation revenue-share accounting.

Implementation: Python (LangGraph) for orchestration; Go services for underlying domains (tenders, compliance, bids). State persists in Postgres via LangGraph's checkpointer pattern.

Full state machine definition in docs/architecture/16-tech-stack-evaluation-and-specs.md §3.2 (private repo)

Spec 3 — The Financial Hedging Spec

A design for tokenised invoice factoring triggered directly by port congestion indices.

The scenario:

  1. Cascadia contractor ships goods via marine vessel to Port of Vancouver
  2. Supplier issues $50K invoice to buyer, payable in 60 days
  3. Supplier wants cash now, not in 60 days
  4. OS detects HIGH port congestion (dwell time >48h, berth occupancy >90%, anchor wait >24h) → shipment delayed
  5. Supplier initiates factoring via OS UI
  6. Investor buys invoice at discount ($47K now for $50K in 60 days)
  7. OS mints factoring token on Polygon (EVM smart contract)
  8. Shipment clears port → smart contract auto-pays token holder
  9. OS takes 1% minting fee ($500 on a $50K invoice)

Congestion index formula (v1.0):

port_congestion_index =
  0.4 × (vessel_dwell_time_hours / median_dwell_time)
+ 0.3 × (berth_occupancy_percent / 100)
+ 0.3 × (anchor_wait_hours / median_anchor_wait)

Index > 1.5 = HIGH congestion
Index > 2.0 = SEVERE congestion
Threshold configurable per supplier

Why port congestion as the trigger: generic factoring exists (BlueVine, Fundbox, traditional banks) — no moat there. Port-congestion-triggered factoring is unique because the OS has real-time logistics data no traditional factor has. The trigger is the congestion index crossing a user-set threshold. The smart contract guarantees payment when shipment clears — trust layer that traditional factoring lacks.

Legal framework: BC PIPA-compliant (no PII in the index); WA UCC Article 9 (invoice factoring = perfected security interest); smart-contract enforceability (case law evolving); cross-border USMCA financial-services chapter + BC Securities Act exemption for accredited investors.

Timeline: Y2 design (congestion index formula + smart contract); Y3 deploy (alongside smart_contracts domain Y3 production); Y3+ launch factoring marketplace; Y4+ volume scaling + cross-port expansion (Seattle, Tacoma, Portland).

Risk + mitigation: Legal risk (smart-contract enforceability varies); liquidity risk (need investor capital); operational risk (congestion index heuristic may mis-trigger). Mitigation: manual override always available; smart contract requires explicit supplier initiation, not automatic execution (per state machine governance).
