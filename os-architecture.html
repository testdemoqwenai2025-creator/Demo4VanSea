Cascadia OS — Architecture

Data Mesh + Event-Driven Architecture: pluggable domains, versioned event contracts

1 Why Not a Monolith

The single most common cause of platform death at year 5–7 is the monolith: a single codebase that has accreted so many features that every change risks breaking something else. The original demo is intentionally monolithic — a single built-output/ directory of static HTML, a single cities-data.json backbone, a single scoring engine. That is the correct shape for a demo. It is the wrong shape for an OS.

The OS commits to two architectural patterns that, together, define how the system breathes: Data Mesh (every domain independently owned and deployable) and Event-Driven Architecture (services communicate via versioned events, not synchronous API calls).

2 The Data Mesh: Domain Map

Every data domain is owned by an independent service with its own storage, schema, team (or agent), and deployment cadence. Domains publish data products to the mesh; no domain writes to another domain's storage.

3 The Event Bus Contract

All cross-domain communication happens via the event bus. Every event has:

FieldPurpose
event_idUUID v7 (time-sortable)
event_typee.g., tender.published, compliance.assessed
event_versionSemantic version — old consumers consume old, new consume new
producerDomain service name (e.g., tenders.ingestor)
schema_urlURL to the JSON Schema — fetched by consumers for validation
payloadConforms to schema_url
provenance_hashSHA-256 of payload + producer signature — anchored monthly
Why schema URL matters

When a producer changes the schema, it bumps event_version and publishes a new schema_url. Old consumers continue consuming old versions; new consumers consume new versions. The producer maintains backward compatibility for at least 2 minor versions. This is what lets the mesh evolve without coordinated rollouts.

4 Worked Example: A New Data Source in 2029

FAA drone delivery telemetry appears. A monolith would have to write a new ingestor, modify the central database schema, coordinate the rollout, and hope nothing breaks. The OS handles it like this:

StepActionTouches existing domains?
1Stand up new drone_telemetry domain — own Postgres, own agents, own deployment cadenceNo
2Publish drone_position.updated events to the busNo
3Existing logistics domain can opt to consume new events by writing a new consumerOptional, one-way
4New Year-9 "last-mile logistics optimizer" can subscribe to both drone + vessel events, joining in real timeNeither producer knows

No core rewrite. No coordinated rollout. The mesh accretes.
