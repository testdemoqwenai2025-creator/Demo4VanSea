Skills — Agent Fleet + Workflow

The Cascadia OS is built on the principle of agentic AI: routine cognitive work is delegated to specialized agents that run continuously and surface exceptions to humans.

20 agents Y1100 agents Y7LangGraphEvent-bus composed

1 Why an Agent Fleet, Not a Single LLM

A 20-year OS cannot bet on a single LLM. The agent fleet decomposition is the architectural choice that lets the OS adopt new AI capabilities incrementally — each agent is replaced individually, validated against its specific contract, with no "rip out the LLM and replace it" project.

The fleet grows from ~20 agents in Year 1 (the wedge) to ~100 agents by Year 7 (platform maturity).

4 The Workflow — How Skills Compose

The skills compose via the event bus. A single user action ("assess this tender for me") triggers a chain of skill invocations:

User clicks "Assess" on tender 2026-Q4-0142
        │
        ▼
  users.search_monitor  ────► publishes compliance.assess.requested event
                                       │
                                       ▼
                        ┌──────────────┼──────────────┐
                        ▼              ▼              ▼
              usmca.assessor    indigenous_procurement.assessor    cca.assessor
                        │              │              │
                        ▼              ▼              ▼
              (each writes to compliance domain; provenance.hasher
               records every claim)
                        │              │              │
                        └──────────────┼──────────────┘
                                       ▼
                            compliance.composer  ────► publishes compliance.assessment.completed
                                       │
                                       ▼
                              (if user.request_draft == true)
                                       │
                                       ▼
                                bid.drafter  ────► publishes bid.draft_generated
                                       │
                                       ▼
                                (user reviews draft in UI; if accepted,
                                 user.ship_bid event published externally;
                                 provenance.hasher records the ship action)

Each arrow is an event on the bus. Each skill is independently deployable, independently replaceable, and independently scorable (latency, accuracy, exception rate).

5 Skill Contracts

Every skill has a formal contract documented in its own .skill.yml file. The contract specifies:

  • skill_id, version, domain
  • trigger (event type + version range, or cron schedule)
  • input_schema (JSON Schema)
  • output_schema (JSON Schema, including provenance hash)
  • failure_modes (conditions + actions + escalation targets)
  • runtime (language, package, memory, timeout)
  • provenance (producer signature key, whether output is recorded)

Skills without a valid contract cannot be deployed. The contract is the unit of versioning; when a skill's behavior changes, the contract version bumps and downstream consumers can opt in.

6 The Human-in-the-Loop Escalation Queue

Every skill has at least one failure mode that escalates to a human. The escalation queue is the OS's safety net — when an agent is uncertain, it does not guess; it escalates. The queue is monitored by the OS operator (in Year 1, the project lead).

Typical escalation volume in Year 1 (forecast)

~50 escalations per week across all skills · ~5–10 requiring same-day response · ~1–2 requiring immediate response (e.g., a sync workflow failure that would break the public preview)
